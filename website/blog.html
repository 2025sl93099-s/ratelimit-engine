What is rate limiting? (And why should you care?)

Imagine you run a coffee shop. If 500 people walk in at the same time, your baristas can't keep up — orders pile up, quality drops, and eventually the whole shop grinds to a halt. Rate limiting is the bouncer at the door. It controls how many people can come in per minute.

😰

Without rate limiting

  • A single user can make 10,000 requests/sec
  • Your server crashes under the load
  • Real users get errors or slow responses
  • A bot can brute-force your login endpoint
  • Your cloud bill spikes unexpectedly
😌

With rate limiting

  • Each user gets a fair share of requests
  • Abuse is blocked automatically with 429
  • Real users always get fast responses
  • Login brute-force is stopped cold
  • Predictable, stable infrastructure costs
What a blocked request looks like
HTTP/1.1 429 Too Many Requests
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
Retry-After: 30

{ "error": "Too Many Requests", "message": "Try again in 30s." }
Part 2 · Choosing an algorithm

Every developer picking their rate limit algorithm

🚶
You
👀
🪣
Token Bucket
"allows bursts"
📅
Fixed Window
"already works fine"
Token Bucket: "I allow short bursts while enforcing a long-term average rate 😏"
Fixed Window: "I'm literally 3 lines of code and handle 99% of use cases 😢"
🪣

Token Bucket

Like a water bucket. Tokens drip in at a fixed rate. You can save them up and burst when you need to. Great for mobile apps that go quiet then suddenly active.

Best for: Public APIs, mobile apps, SDKs
🪟

Sliding Window

Always looks back 60 seconds. No boundary spikes, no burst. Every request counted evenly across time — smooth and fair.

Best for: Search, feeds, anything needing fairness
📅

Fixed Window

Counts in hard time slots. Simple. Cheap. Has a known weakness: 100 requests at 11:59 + 100 at 12:00 = 200 in 2 seconds.

Best for: Login throttle, admin routes, dev environments
💧

Leaky Bucket

Requests drip out at a fixed rate no matter how fast they come in. Excess is dropped immediately. Maximum predictable output.

Best for: Protecting databases, downstream APIs

Part 4 · The Fixed Window trap

The Fixed Window boundary problem, visualised

😰
Your rate limiter
11:59:50 100 requests arrive → all allowed ✅
12:00:00 ⚠ Window resets
12:00:01 100 MORE requests → all allowed ✅
result 200 requests in 11 seconds 🔥 limit was 100/min

Fix: Use SlidingWindow — it weights the previous slot so this spike never happens.

Part 6 · When Redis goes down

fail-open vs fail-closed

🙅
Blocking ALL requests when Redis goes down
(failClosed — your site is down)
👉😎
failOpen: true — allow traffic through when store is unavailable, log a warning, keep running (your site stays up)
Configure fail-open in one line
const limiter = createLimiter({
  algorithm: new TokenBucket({ capacity: 100, refillRate: 10 }),
  store:     new RedisStore({ client: redis }),
  failOpen:  true,   // ← Redis down? Allow traffic, log warning
  keyBy:     byIP,
})
Part 7 · Galaxy brain engineering

Rate limiting levels — ascending brain power

🧠
No rate limiting
Ships fast. Gets DDoS'd by Thursday.
🧠
Fixed Window on everything
limit: 100, windowMs: 60000 — good enough for 90% of APIs.
🧠
Token Bucket per user + Redis
Distributed. Burst-friendly. Works across 10 servers. Now we're cooking.
🧠
Composite: TokenBucket AND SlidingWindow
Burst cap + daily hard limit + per-route overrides + failOpen + live dashboard. Ascended.
The galaxy-brain config
const limiter = createLimiter({
  algorithm: new Composite({
    algorithms: [
      new TokenBucket({ capacity: 50, refillRate: 10 }),     // burst cap
      new SlidingWindow({ limit: 500, windowMs: 86_400_000 }),// daily limit
    ],
    mode: COMPOSITE_MODES.ALL,  // BOTH must pass
  }),
  store:    new RedisStore({ client: redis }),
  keyBy:    byUser,
  failOpen: true,
})

Engineering

What happens when Redis goes down? fail-open vs fail-closed

Every rate limiter must answer one question: what do you do when the store is unavailable? failOpen: true keeps your site up. failOpen: false keeps it strictly enforced.

Request → Redis down → failOpen → ✅ allow

Composite rate limiting — burst caps AND daily limits at once

Stack two algorithms with ALL mode. A request must pass both to get through. Enforce burst caps without relaxing daily hard limits.

Why MemoryStore isn't enough when you scale to multiple servers

Two instances of your app means two independent counters. Redis with atomic Lua scripts is the only correct solution.

❌ Memory S1: 100/100 S2: 100/100 200 slip through
✅ Redis S1+S2 → 100 total

Best Practices

Rate limit by IP, user, route — or all three at once

IP-based is easy but unfair on shared networks. User-based is accurate. Route-based lets you fine-tune per endpoint. Combine them all.
