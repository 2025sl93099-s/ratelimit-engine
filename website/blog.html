What is rate limiting? (And why should you care?)

Imagine you run a coffee shop. If 500 people walk in at the same time, your baristas can't keep up — orders pile up, quality drops, and eventually the whole shop grinds to a halt. Rate limiting is the bouncer at the door. It controls how many people can come in per minute.

😰

Without rate limiting

  • A single user can make 10,000 requests/sec
  • Your server crashes under the load
  • Real users get errors or slow responses
  • A bot can brute-force your login endpoint
  • Your cloud bill spikes unexpectedly
😌

With rate limiting

  • Each user gets a fair share of requests
  • Abuse is blocked automatically with 429
  • Real users always get fast responses
  • Login brute-force is stopped cold
  • Predictable, stable infrastructure costs
What a blocked request looks like
HTTP/1.1 429 Too Many Requests
X-RateLimit-Limit: 100
X-RateLimit-Remaining: 0
X-RateLimit-Reset: 1700000060
Retry-After: 30

{
  "error": "Too Many Requests",
  "message": "You've hit the rate limit. Try again in 30 seconds."
}

Token Bucket vs Sliding Window — which one should you use?

This is the most common question developers ask when adding rate limiting. Here's the honest answer — it depends on your traffic pattern. Let's break each one down with simple analogies.

🪣

Token Bucket

Think of it like a water bucket. Tokens drip in at a fixed rate. Each request uses one token. You can save up tokens and burst when needed — great for APIs where users occasionally make many requests at once.

Best for: Public APIs, mobile apps, anything with natural burst traffic
🪟

Sliding Window

A rolling 60-second window that always looks back. No burst allowed. Every request is counted evenly across time — no boundary spike like Fixed Window has. Smoother, fairer limiting.

Best for: Search APIs, feeds, anything that should feel smooth and consistent
📅

Fixed Window

Counts requests in hard time slots — e.g. exactly 100 per minute. Simple and cheap, but has a known weakness: a user can make 100 requests at 11:59 and 100 more at 12:00, getting 200 requests in 2 seconds.

Best for: Login attempts, low-traffic admin routes, anywhere simplicity wins
💧

Leaky Bucket

Like a bucket with a hole in it — requests drip out at a fixed rate no matter how fast they come in. Excess is dropped. This gives you the most predictable output rate.

Best for: Protecting downstream services, databases, third-party APIs with strict rate limits

Quick Start Guide 3 min read

Add rate limiting to your Express app in 5 minutes

No experience needed. Here's exactly what to type.

1

Install the package

npm install ratelimit-engine
2

Run the setup wizard — it writes the config for you

npx ratelimit-engine

The wizard asks 5 questions and generates a ratelimit.config.js file in your project. No manual config.

3

Import and wire it into your app

import { limiter } from './ratelimit.config.js'
import express from 'express'

const app = express()

// Protect your entire API
app.use(limiter.express())

// Or just one route
app.post('/login', limiter.express(), (req, res) => {
  res.json({ message: 'Logged in!' })
})

app.listen(3000)
4

Watch it work — open the live dashboard

npx ratelimit-engine dashboard

A real-time terminal dashboard shows every request — allowed vs blocked — at 10ms resolution. Run your app and fire some requests to see it light up.
